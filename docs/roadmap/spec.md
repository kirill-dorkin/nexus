## 1. Цель

**Ближайшая цель:** первые 10–20 приглашённых учеников уже учатся на опубликованном маршруте HTML → CSS, сохраняют прогресс, сдают практику и дают обратную связь. Бесплатное место в бете сохраняется при понятной недельной норме.

### 1.1 Порядок до первого набора

1. **B0 — запустить первую волну с координатором.** Сначала 5 учеников проходят настоящий учебный путь, затем набор до 20. План недели и обратная связь через существующий согласованный канал; новые таблицы и страницы не нужны.
2. **B1 — перенести контроль в продукт.** Своя неделя, серверные счётчики, отзыв, экран координатора и восстановление доступа. Первая волна в это время продолжает учиться.
3. **После двух полных недель — решение о расширении.** Основания: активация, возвращаемость, самостоятельные работы и устранённые препятствия. Точные нормы, метрики и критерии в [beta-launch.md](beta-launch.md).

Бета не ждёт P1.1–P1.7 целиком, нового дизайна, всех персонажей, грейдера или подписок. Разработка не блокирует существующее бесплатное обучение. Отсутствующая функция не показывается как работающая.

### 1.2 Следующие рубежи

- Проверяемые тесты навыков, серверные опоры и интервальное повторение.
- Подписка «Искатель» после проверки беты и готовности продления, отмены и возвратов.
- Практика с исполнением кода и следующие сезоны.
- Ревью, наставники и командные проекты после появления людей для этих услуг.

Недельная норма — условие участия в бете, а не новая модель Mastery и не условие доступа к уже публичным бесплатным курсам.

## 2. Правила работы

### 2.1 Порядок одного пакета

1. **Ветка от свежего `main`.** Один пакет — одна ветка — один PR. Большой пакет делится на PR, каждый из которых сам по себе рабочий.
2. **Перед кодом:** прочитать затронутый код, тесты, ADR. Новое долговременное решение — сначала ADR в том же PR.
3. **Перед пушем `pnpm check`** под общей блокировкой:
   ```bash
   until mkdir /tmp/nexus-heavy-check.lock 2>/dev/null; do sleep 30; done
   trap 'rmdir /tmp/nexus-heavy-check.lock' EXIT   # только после успешного mkdir
   ```
   Для затронутого API — интеграционные тесты, для затронутого Web — e2e (после сборки `NEXT_PUBLIC_API_ORIGIN=/ pnpm build`), под той же блокировкой.
4. **PR → CI `verify` зелёный → squash-слияние** своего PR → проверка продакшена: `/v1/health` показывает релиз (первые 12 символов SHA), затронутые страницы отвечают 200.
5. Красный CI чинится в том же PR. Новый PR ради починки не открывается.

### 2.2 Изменения базы

- Применяются сами перед каждой выкладкой `main` (ADR-0079). Значит, изменение базы и код к нему можно сливать вместе.
- Изменения только **аддитивные и совместимые с работающей версией**. Удаление колонок и таблиц — отдельным PR, после решения владельца.
- Новые таблицы — с RLS по организации. Защищённые ответы и эталоны никогда не попадают в публичные данные.
- Неслитое изменение базы **не применять** к общей локальной базе: она общая для всех сессий. Проверять SQL откатываемой транзакцией и тестом в CI.

### 2.3 Можно без вопросов

Код, тесты, ADR, документация, контент (уроки, вопросы, сцены), изменения базы, слияние своих зелёных PR, проверка продакшена, параллельные сессии — до 4, каждая в своём worktree и на своих файлах.

### 2.4 Только с владельцем

- Публикация курсов: нужен пароль владельца, агент его **не использует**. Агент готовит точные команды.
- Включение оплаты и цены.
- Включение грейдера в продакшене.
- Юридические тексты.
- Выбор провайдеров (почта, платежи, хостинг фоновых процессов).
- Замена главной страницы.
- Удаление данных учеников.
- Необратимые изменения схемы.

Если пакет упёрся в такое решение — делать следующий пакет, а вопрос вынести в отчёт.

### 2.5 Если продакшен сломался

Если после слияния продакшен отвечает не 200 или release не совпадает:
1. сразу открыть revert-PR и слить его после CI;
2. потом разбираться.

Изменение базы откатывается только новым изменением базы.

### 2.6 Контент

- Полное покрытие темы, своими словами, без внешних ссылок «почитай там».
- Сюжет живёт только в игровой оболочке (сцены, карта); объяснения в уроках нейтральные.
- Старая история про кофейню под запретом.
- Каждая новая сущность контента проходит тесты конвейера (раздел 4, фаза 4).
- Для B0 проверяем законченный стартовый маршрут и запас на две недели. Полное покрытие технологии и новые персонажи не являются условием первого набора.

## 3. Определение готовности пакета

Пакет готов, когда:
- слит PR с зелёным CI, продакшен проверен;
- новое поведение покрыто тестами: unit; HTTP + PostgreSQL для API; компонентные и e2e с axe для Web;
- бюджеты производительности не выросли без объяснения;
- `current-state.md` обновлён, если изменились возможности, рубеж или следующий пакет;
- ADR добавлен или поправлен, если изменилось долговременное решение;
- для действий владельца в PR и отчёте записаны точные шаги.

## 4. Пакеты работ

Объём указан в днях работы агента: **S** до 1, **M** 1–3, **L** 3–6. Это оценки разработки, а не обещание срока запуска.

**Первый исполняемый пакет — B0 из [beta-launch.md](beta-launch.md), затем B1.** Фазы ниже сохраняют идентификаторы и описывают дальнейшее развитие. Пакеты выбираются по реальным зависимостям; закрытие целой фазы 1 не требуется для начала беты. Уже начатые небольшие PR доводятся отдельно, не задерживая первый учебный маршрут.

### Фаза 1 — Прокачка по-настоящему (~1 неделя)

**Итог фазы:** навык засчитывается только тестом навыка, срок и опоры проверяет сервер, а карта живёт в базе.

#### P1.1 Тест навыка — L (ADR-0075, база 000050 готова)

**Сделать:**
- **Манифест курса.** Блок `skillTests: [{ skillKey, questions: [...] }]`. Типы вопросов:
  - `single_choice`, `multiple_choice`, `short_text`;
  - `code_output` и `find_bug` (single choice с блоком кода).
  У каждого вопроса стабильный `key` и объяснение каждого неверного варианта.
- **Импорт.**
  - На каждый навык с банком — активность `skill.test` в версии курса; банк кладётся в `learning_content.skill_test_banks`.
  - Проверки при импорте: не меньше 12 вопросов на навык (флаг `--allow-small-banks` только для e2e-фикстуры); уникальные ключи; верные ответы есть среди вариантов.
  - Публичные данные урока не содержат ответов.
- **Начать тест:** `POST /v1/me/learning/:org/skills/:skillKey/tests` с ключом выдачи (UUID).
  - Сервер берёт 5 вопросов: сначала те, что ученик видел реже.
  - Запись идёт в `skill_test_draws`; повтор с тем же ключом возвращает ту же выдачу.
  - В ответе только формулировки и варианты.
- **Сдать:** `POST …/tests/:drawKey/submission`, все 5 ответов разом.
  - Сервер проверяет ровно выданные вопросы.
  - Attempt → Submission → ValidationResult (`skill_test@1`) → Evidence на навык.
  - Порог 4 из 5. Неверные ответы возвращаются с объяснениями. `attempt_id` у выдачи пишется один раз.
- **Ограничения:**
  - пересдача через 10 минут после провала (`409 retake_cooldown` со временем);
  - лимит частоты по ADR-0070;
  - проверки Origin и своей записи на курс — как у квизов.
- **Экстерн ветки:** `POST …/branches/:branchId/tests` — по вопросу на навык; сдал — Evidence на каждый навык ветки.
- **Web:**
  - страница теста `/characters/{slug}/skills/{skillKey}/test`: вопросы по одному, итог, разбор ошибок, кнопка «Пересдать» с таймером;
  - на профиле персонажа кнопка «Подтвердить» ведёт на тест, а не на урок.

**Приёмка:**
- Интеграционные тесты: выдача стабильна по ключу; нельзя сдать чужие или невыданные вопросы; 4 из 5 даёт подтверждение и `confirmedDays`; 3 из 5 — нет; пауза 10 минут; ответы не утекают ни в публичный урок, ни в выдачу.
- e2e: ученик проходит тест в фикстуре, и уровень персонажа растёт; axe без нарушений.

#### P1.2 Банк вопросов HTML — L (контент, параллельно P1.1)

**Сделать:** по 12–15 вопросов на каждый из 68 навыков HTML в `docs/examples/html-course/` (по файлу банка на модуль). Типы перемешаны: не меньше 3 «что выведет / как отобразится», «найди ошибку» или «порядок».

**Приёмка:**
- тест контента: у каждого навыка не меньше 12 вопросов; ответы уникальны и есть среди вариантов; у каждого неверного варианта объяснение;
- нет запрещённых слов и внешних ссылок;
- манифест пересобран.

После слияния курс HTML нужно опубликовать заново (владелец, `--new-version`).

#### P1.3 Карта навыков в базе — M (ADR-0078, база 000051 готова)

**Сделать:**
- Манифест `skill-map@2`: тот же документ, что сейчас строит `docs/examples/skill-map/build.mjs`, плюс `prerequisites` по навыкам и ссылки на сцены.
- `POST organizations/:org/skill-maps/manifest/{validate,apply}` и публикация. Проверки:
  - каждый навык существует;
  - навык принадлежит ровно одному персонажу;
  - граф без циклов;
  - индексы покрытия покрыты.
- Публичное чтение `GET /v1/public/skill-map/:org`.

**Приёмка:** интеграционные тесты импорта, публикации, неизменяемости опубликованной версии и RLS; e2e страниц персонажей на карте из API.

- Web показывает, что подтвердить сначала, со ссылками.

**Приёмка:** интеграционный тест: забытая опора закрывает тест, а после её подтверждения тест открыт.

## 6. Риски

| Риск | Мера |
|---|---|
| Первый набор откладывается ради новых функций | B0 на готовом маршруте; B1 во время обучения; подписки, грейдер и полное покрытие не являются блокерами |
| Тысячи вопросов, десятки персонажей | Сначала результаты одного маршрута с учениками; затем конвейер, тесты и преподавательская редактура |
| Норма провоцирует пустые баг-репорты | Один учебный отзыв, вариант «проблем не заметил», ошибки продукта не являются обязательной квотой |
| Ученика наказывают за сбой или изменение контента | Зафиксированный план, исключение/пауза координатора, сохранение прогресса и публичного бесплатного доступа |
| Изменения базы применяются при слиянии | Только аддитивные; staging (P3.5); проверка восстановления |
| Для оплаты и других фоновых последствий нет production host | P2.1 перед включением соответствующих процессов; запуск бесплатной беты от этого не зависит |
| Условия работы с данными и оплаты для выбранной аудитории не финализированы | Владелец завершает #174 и решения по провайдерам до соответствующего расширения; бета не выдаёт себя за платную подписку |
| Исполнение кода учеников | Изоляция gVisor, проверка безопасности, включение только по решению владельца |
| Минуты GitHub Actions | Документация без CI, отмена устаревших прогонов, тяжёлые проверки локально; бюджет $20 |

## 7. Отчёт

После каждого пакета — коротко владельцу:
- что изменилось для ученика;
- ссылка на PR;
- что проверено в продакшене;
- что нужно от владельца.

Раз в день — сводка: фаза, сделано, осталось, решения.

Для беты отдельно: сколько людей приглашены, активировались и сделали первую попытку; сколько выполнили норму; какие препятствия мешают учиться и кто их разбирает. Отделять готовое ТЗ и страницы от фактического начала обучения.
