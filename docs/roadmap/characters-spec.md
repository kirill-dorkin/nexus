# Техническое задание: прокачка персонажей вместо курсов

Версия 1, 2026-11-05. Владелец поставил задачу: учёба строится не как список курсов, а как прокачка персонажей с картой навыков и в игровой манере. Персонажи: ПК, Браузер, HTML, CSS, JavaScript, SQL и следующие. Нужна и ценовая политика.

Документ рассчитан на автономную ночную работу агента. Порядок источников истины — по `AGENTS.md`. Принятые ADR и код важнее этого документа.

## 1. Что уже есть и на чём строим

- **Навыки общие для организации.** Таблица `learning_content.skills`, ключ `(organization_id, skill_key)`. Навык `css-selectors-basic` один и тот же в любом курсе.
- **Mastery считается на ученика и навык по всей организации** (`learning_progress.mastery_projections`, ADR-0005, ADR-0023). Курс только показывает часть навыков. Значит, прокачка персонажа — это чтение уже существующей Mastery по его навыкам. Новых данных о прогрессе не нужно.
- **Цепочка Evidence → Mastery уже работает.** Её пополняют квизы и домашние задания. Практика в браузере Evidence не даёт (ADR-0064).
- **В опубликованных курсах 289 навыков:** HTML 70, CSS 53, JS 114, SQL 52. Навыки `web-*` из HTML-курса по смыслу относятся к Браузеру. Неопубликованный курс «Как устроен компьютер» (4 навыка `computer-*`) — заготовка для ПК.
- **Commerce:** Product с неизменяемой Price, разовая оплата через Paddle и Entitlement (ADR-0044–0052). Подписок нет. Оплата в продакшене выключена.

## 2. Модель

| Понятие | Что это | Где живёт |
|---|---|---|
| **Персонаж** | Предметная область, которую ученик прокачивает: ПК, Браузер, HTML, CSS, JavaScript, SQL. Имя, роль («Строитель страниц»), цвет, иконка, описание. Это не сюжет и не герой истории: правило «без сюжета» остаётся в силе. | Карта навыков |
| **Навык персонажа** | Существующий Skill организации. Каждый навык принадлежит ровно одному персонажу. | Карта навыков ссылается на `skill_key` |
| **Связь «нужно раньше»** | Ребро навык → навык, в том числе между персонажами (CSS-селекторы требуют HTML-элементов). Граф без циклов. | Карта навыков |
| **Опыт (XP) персонажа** | Сумма Mastery его навыков × 100. Навык с Mastery 0.8 и выше считается освоенным. | Вычисляется, не хранится |
| **Уровень** | Растёт по доле освоенных навыков: 0 → 1 → … → 10. 10 — все навыки освоены. Пороги — в карте. | Вычисляется |
| **Состояние навыка** | `locked` — не освоены требования, `open` — можно учить, `progress` — есть Evidence, `mastered` — Mastery не ниже 0.8. `locked` — только подсказка, а не запрет: доступ по-прежнему решают Enrollment и Entitlement. | Вычисляется |
| **Задание (квест)** | Урок, в котором навык тренируется: ссылка на существующий урок курса. | Из опубликованных курсов |

**Почему так.**
- Mastery и Evidence не меняются, поэтому история учеников остаётся.
- Курсы остаются источником контента. Персонажи — новый способ видеть и проходить тот же контент.

## 3. Этапы

### Этап 1 (ночь): карта как версионированный файл в репозитории, интерфейс поверх Mastery

Миграций нет: владелец спит, а выкладка миграции не применяет.

- **N1. ADR-0074** «Персонажи и карта навыков».
  - Персонаж — способ показать навыки, не новая единица доступа.
  - Прогресс берётся только из Mastery.
  - Карта на этапе 1 — неизменяемый версионированный файл `skill-map@1` в репозитории, аналог порядка курсов в ADR-0066.
  - На этапе 2 она переходит в Learning Content и становится публикуемой версией, как курс.
- **N2. Карта `packages/contracts/src/skill-map/`.**
  - Схема `skillMapSchema` (zod) и данные: персонажи, принадлежность всех 289 навыков персонажам, рёбра «нужно раньше», пороги уровней.
  - Тесты:
    - каждый навык опубликованных манифестов принадлежит ровно одному персонажу, лишних ключей нет;
    - граф без циклов;
    - у каждого персонажа есть описание и хотя бы один навык;
    - запрещённые слова сюжета не встречаются.
- **N3. API:** `GET /v1/me/skills/{org}` — собственная Mastery ученика по всем навыкам организации.
  - Правило доступа как у своих квизов: только свой пользователь, роль не нужна.
  - Состав и формат ответа как в learner contract ADR-0023: состояние, score и число Evidence.
  - Только чтение, без миграции. Интеграционный тест на PostgreSQL: свой и чужой пользователь, аноним, неизвестная организация.
- **N4. Web: страница «Карта навыков» `/map`.**
  - Персонажи карточками с уровнем и полосой опыта.
  - Под ними граф навыков выбранного персонажа: узлы по состояниям, рёбра, клавиатурная навигация и альтернатива списком для доступности.
  - Аноним видит карту с нулевым уровнем и призыв начать.
- **N5. Web: страница персонажа `/characters/{slug}`.**
  - Уровень, опыт до следующего уровня, «следующий навык» — первый `open` по порядку.
  - Навыки по главам со статусами, у каждого — задания-уроки со ссылками на уроки.
  - «Требует персонажей» — входящие рёбра от других персонажей.
- **N6. Встраивание.**
  - Ссылка «Карта навыков» в шапке.
  - На странице курса блок «Какие персонажи прокачиваются».
  - В «Моё обучение» — уровни персонажей.
  - Главная и каталог курсов **не заменяются** до решения владельца (раздел 6).
- **N7. Качество.**
  - Компонентные тесты расчёта уровня и состояний.
  - e2e: аноним открывает карту и персонажа; ученик решает квиз, и уровень персонажа растёт.
  - axe и бюджеты размера страниц.

### Этап 2 (после решения владельца, с миграциями)

- Карта навыков становится публикуемой неизменяемой версией в Learning Content: импорт `skill-map@1`, редактор в Studio.
- Главная становится картой персонажей. Курсы уходят в «Задания персонажа».
- Контент новых персонажей:
  - ПК — на основе курса «Как устроен компьютер», расширенный до полного;
  - Браузер — навыки `web-*` плюс DevTools, сеть, адресная строка, вкладки, безопасность.
  - Публикует владелец.
- Игровые механики поверх Evidence:
  - серии дней;
  - достижения: первый освоенный навык, уровень 5, персонаж на максимуме;
  - ежедневное задание — навык, который пора повторить (политика повторения ADR-0038 уже есть).

### Этап 3: ценовая политика

Варианты с рекомендацией — в `docs/roadmap/pricing-proposal.md`, который агент пишет ночью. Цены не включаются: оплату в продакшене включает только владелец (раздел 6).

## 4. Ночной порядок работы

1. N1–N2: ADR, схема и данные карты, тесты, PR, CI, слияние. Продакшен не меняется.
2. N3: API, интеграционный тест, PR, слияние, проверка `/v1/health` release.
3. N4–N5: страницы, тесты, e2e, PR, слияние, проверка `/map` и `/characters/html` в продакшене (200, без ошибок в консоли).
4. N6–N7.
5. Предложение по ценам.
6. Технические хвосты из прошлого ТЗ:
   - лимит размера манифеста JS (859 КБ при лимите тела 1 МБ);
   - CLS каталога 0.099;
   - нестабильная browser-launch проверка.
7. Черновик контента персонажей ПК и Браузер — как PR-черновик, без публикации.

Каждый пункт идёт отдельной веткой и PR по `docs/engineering/development-workflow.md`:
- локально `pnpm check` под общей блокировкой, интеграционные тесты и e2e для затронутого;
- затем CI, squash-слияние и проверка продакшена.

## 5. Правила ночной работы

- Можно: код, тесты, ADR, документацию; сливать свои зелёные PR; добавлять новые страницы и ссылки на них.
- Нельзя без владельца:
  - миграции продакшена и PR, требующие их до выкладки кода;
  - включение оплаты и цены;
  - публикация курсов;
  - замена главной и каталога;
  - удаление контента;
  - force push.
- Если продакшен после слияния отвечает не 200 или release не совпадает — сразу revert-PR, затем разбор.
- Сюжета нет, внешних ссылок «почитать там» нет — правила контента прежние.
