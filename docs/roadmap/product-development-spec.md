# Техническое задание: следующий этап развития Nexus

Версия 1, 2026-11-04. Документ фиксирует фактическое состояние платформы на `main` 64a791e и задаёт работы следующего этапа: цели, требования, критерии приёмки и порядок. Порядок источников истины — по `AGENTS.md`: код, миграции и тесты важнее этого документа; принятые ADR важнее него; это планирующий документ.

## 1. Итог анализа

**Архитектура выполнена корректно и с запасом.** Модульный монолит соблюдает свои правила: модули общаются через публичные application-интерфейсы, все таблицы с данными организаций защищены RLS, бизнес-состояние и событие outbox пишутся в одной транзакции, домены (Content/Delivery, Attempt/Submission, ValidationResult/Evidence, Product/Price/Purchase/Entitlement/Enrollment) разделены так, как описано в ADR. Бэкенд покрыт интеграционными тестами на PostgreSQL (321 тест), фронт — компонентными и e2e-тестами с axe и бюджетами производительности.

**Продукт использует меньшую часть того, что построено.** В продакшене работает только бесплатное обучение: каталог, уроки, практика в браузере, квизы, «Моё обучение», Studio. Примерно половина возможностей бэкенда не имеет интерфейса или не запущена (раздел 2). Отсюда главный вывод этапа: не строить новые подсистемы, а довести до ученика то, что уже есть, начиная с практических заданий с автопроверкой.

**Найдено несколько архитектурных отклонений** (раздел 3). Критичных для безопасности среди них нет; два касаются того, что заявленный механизм фоновой обработки фактически не запущен.

## 3. Архитектурные отклонения

| # | Что | Почему важно | Что сделать |
|---|---|---|---|
| A1 | `events.outbox` только пишется: в коде нет ни одного читателя или ретранслятора | Правило «отложенные последствия идут через outbox» сейчас декларативно; первый потребитель придётся строить с нуля | Решить в ADR: либо outbox пока остаётся аудит-журналом (зафиксировать это явно), либо добавить relay вместе с первым реальным потребителем (Э4 или Э6) |
| A2 | `GitHubWebhookLifecycleProcessor` и `GitHubProjectFactProcessor` не запускаются ни одним процессом, только тестами | Конвейер GitHub (ADR-0029–0031) в рантайме мёртв: вебхуки принимаются, но не обрабатываются | Подключить к worker при активации F6 или пометить в `current-state` как неактивный |
| A3 | `projects` импортирует `GitHubProjectFactDeliveryRepository` из `integrations` | Формально это application-слой, но по смыслу — чужой репозиторий; ADR-0031 отвергает связь Projects с хранилищем Integrations | Переименовать в публичный порт (`…DeliveryPort`) с узким контрактом claim/ack |
| A4 | Нет автоматической проверки границ модулей | Правило держится на ревью; следующее нарушение пройдёт незамеченным | Архитектурный тест: импорт из чужого модуля разрешён только из `application/*.query.ts`, `*.port.ts`, `*.command.ts` и публичных типов |
| A5 | Открыты окна совместимости F4 (`attempts.submission`, событие `attempt.submitted`, Evidence-by-Attempt) | Без внешних клиентов закрыть их дёшево; после запуска заданий (Э1) станет дорого | Срез очистки до Э1: миграция и удаление переходных путей |
| A6 | Фоновые процессы (worker оплаты, worker грейдера, обработчики GitHub) не имеют хостинга в продакшене | Vercel Services разворачивает только Web и API; любая функция с очередью сейчас не может быть включена | Решение о хостинге воркеров (Э6) до включения оплаты, GitHub или серверного грейдера |
| A7 | ADR-0060 (вход через Google/GitHub) реализован, но в статусе Proposed; раздел «Open work» в `current-state` устарел (#97–#104 закрыты, #46 заменён слитым #45) | Документы расходятся с кодом | Принять ADR-0060, обновить `current-state`, закрыть #46 |

RLS проверен по всем 64 таблицам: без RLS только глобальные таблицы (`identity.*`, `access_control.roles`), что соответствует модели.

## 4. Цели этапа

1. **Ученик выполняет практические задания вне браузера и получает автоматическую обратную связь**: скачивает задание, делает его у себя, сдаёт архив, видит, что исправить, и пересдаёт.
2. **Ученик видит, чему научился**: прогресс по навыкам из уже существующей Mastery.
3. **Владелец видит, как проходят курсы**: обезличенная воронка по шагам урока.
4. **Платформа готова к фоновой обработке**: долг A1–A7 закрыт, воркеры имеют место для запуска.

North Star из `product-constitution.md` — подтверждённые навыки на активного ученика. Цели 1–3 впервые делают его измеримым.

Вне этапа (не начинать без отдельного решения): запуск грейдера в продакшене для произвольных языков, когорты с преподавателем, GitHub-проекты, оплата, рекомендации в интерфейсе.

## 5. Эпики и требования

Сложность: S — до 3 дней, M — до 2 недель, L — больше. Каждый эпик делится на срезы по `development-workflow.md`: ветка → черновой PR → зелёный CI → локальная проверка → squash.

### Э0. Архитектурная гигиена — S–M, первым

- A5: закрыть окна совместимости F4 миграцией; удалить переходные пути API и событие-алиас.
- A4: архитектурный тест границ модулей в `tests/architecture/`.
- A3: публичный порт вместо чужого репозитория.
- A1, A2: ADR-решение по outbox и статусу GitHub-конвейера.
- A7: ADR-0060 → Accepted, `current-state` актуален, #46 закрыт.

**Приёмка:** тест границ падает на искусственном нарушении и зелёный на `main`; в API нет маршрута Evidence-by-Attempt; `current-state` совпадает с GitHub.

### Э1. Задания с автопроверкой — L, главный эпик

**Сценарий ученика.**
1. На странице урока блок задания: условие, кнопка «Скачать задание» (zip с заготовками и `README`), критерии.
2. Ученик делает задание локально и загружает zip или отдельный файл (перетаскиванием или выбором файла).
3. Через секунды видит отчёт: список проверок с отметкой «пройдено / нет», для непройденных — что не так, где (файл, по возможности строка) и подсказка. Отчёт доступен с клавиатуры и скринридером.
4. Пересдаёт сколько угодно раз; каждая сдача — новая попытка, история видна.
5. Засчитанная сдача отражается в «Моём обучении» и в навыках (Э2).

**Сценарий автора.** В манифесте курса и в Studio автор описывает задание: условие, файлы-заготовки, список проверок, навыки. Предпросмотр позволяет сдать эталонное решение и увидеть все проверки зелёными.

**Данные и контракты.**
- Новый тип активности в манифесте, например `assignment.files`, с полями: `starterFiles` (путь → содержимое), `allowedFiles` (маски путей и расширений), `checks` (декларативные проверки тех же видов, что у практики: DOM-селекторы и атрибуты, CSS-свойства, JS-тесты вида «вызов → ожидаемый результат», SQL-запрос → ожидаемая таблица), `skillKeys`. Проверки — защищённый контент, как ключи квизов: ученику показываются только формулировки, не эталоны.
- Сдача ложится в существующую цепочку: Attempt → Submission с `payload = { files: { "index.html": "…" } }` → ValidationResult → Evidence. Новые таблицы для файлов не нужны, пока сдача текстовая.
- Лимиты (проверяются в браузере и повторно на сервере): архив до 1 МБ, распакованно до 2 МБ, до 50 файлов, только разрешённые расширения, глубина путей до 5, без абсолютных путей и `..`; бинарные файлы отбрасываются с предупреждением. Защита от zip-бомб — ограничение распакованного размера до распаковки.

**Где выполняется проверка — по шагам.**

| Шаг | Проверка | Доверие | Что даёт |
|---|---|---|---|
| 1.1 | В браузере, теми же движками, что практика; сдача сохраняется как Submission | Результат — практика (ADR-0064), Evidence не создаётся | Обучающая ценность сразу, без новой инфраструктуры |
| 1.2 | Повтор проверок HTML/CSS на сервере синхронно в API: только разбор, без выполнения кода | Доверенный ValidationResult → Evidence | Засчитанные навыки за задания по HTML/CSS |
| 1.3 | JS и SQL на сервере в изолированном WASM-движке (QuickJS/PGlite) с лимитами времени и памяти, в отдельном процессе | Доверенный, если ADR подтвердит модель угроз | Засчитанные навыки по JS/SQL |
| 1.4 | Грейдер с песочницей (существующий F7) | Полное | Python, бэкенд, многофайловые проекты; только по отдельному решению |

Шаги 1.3 и 1.4 требуют ADR: выполнение кода ученика вне браузера — граница безопасности по ADR-0007.

**API (шаг 1.1–1.2).** Используются существующие маршруты попыток и сдач; добавляется сокращённый маршрут для ученика по образцу квиза (`/v1/me/learning/…/assignments/:activity/submissions`), возвращающий отчёт. Ошибки инфраструктуры — `system_error`, никогда не «ученик ошибся».

**Приёмка Э1.**
- e2e: скачать задание → загрузить эталон → все проверки зелёные; загрузить решение с ошибкой → видны конкретные пункты; исправить → засчитано.
- Отчёт проходит axe и клавиатурный тест; страница урока укладывается в бюджет JS (+ не более 30 КБ на загрузку и распаковку, загрузка по требованию).
- Интеграционные тесты: лимиты, вредоносные архивы, чужая организация (RLS), повторная сдача, отсутствие утечки эталонов в ответах.
- Шаг 1.2: результат сервера совпадает с результатом браузера на общем наборе фикстур (один и тот же движок проверок в общем пакете).

**Технические требования.** Движок проверок практики выносится из `apps/web` в общий пакет (например, `@platform/checks`) без зависимостей от DOM браузера, чтобы одна реализация работала в браузере и в API; для HTML на сервере — парсер, эквивалентный `DOMParser` (например, `parse5`), с тестами эквивалентности.

### Э2. Прогресс навыков для ученика — M

- В «Моём обучении» и на странице курса: навыки курса и уровень освоения из существующей Mastery (`/users/:id/mastery`), с понятной шкалой и пояснением «за что засчитано» (ссылки на квизы и задания).
- Только собственные данные ученика; формулировки без внутренних терминов.
- **Приёмка:** после засчитанного квиза или задания навык меняется на странице без перезагрузки сессии; e2e и axe зелёные.

### Э3. Воронка обучения — M, нужен ADR

- Обезличенные агрегаты по шагам: открыт урок → практика решена → квиз сдан → регистрация → следующий урок. Счётчики по курсу, уроку и дню; без идентификаторов пользователей, без адресов и текстов (по правилам ADR-0052/0067).
- Источник для действий авторизованного ученика — канонические события (Submission, Evidence, Enrollment); для анонимных шагов — клиентские события с тем же контрактом, что у телеметрии.
- Экран в Studio для владельца организации: таблица по урокам и место наибольшего отсева.
- **Приёмка:** ADR принят; e2e-сценарий меняет счётчики ожидаемо; никаких персональных данных в хранилище (тест на схему).

### Э4. Задания в Studio — M

- Ручной редактор и JSON для `assignment.files`: заготовки, разрешённые файлы, проверки, навыки; проверка эталонного решения в предпросмотре.
- **Приёмка:** автор создаёт задание без JSON; публикация отклоняет задание, у которого эталон не проходит собственные проверки.

### Э5. Курсы с заданиями — M (контент)

- В каждый из четырёх курсов маршрута — задания «скачай и сдай» в конце глав, по правилам контента (`docs/` и память проекта: без сторителлинга, без внешних переходов, полное покрытие темы).
- **Приёмка:** курсы опубликованы владельцем командой `launch-course.mjs`; каждое задание проходит эталонное решение.

### Э6. Хостинг фоновых процессов — M, перед включением оплаты, GitHub или грейдера

- Выбрать место запуска воркеров (отдельный контейнерный хостинг или cron/queue платформы), роли БД — существующая `platform_worker`.
- Запустить: worker оплаты (ADR-0045 и далее), обработчики GitHub (A2), relay outbox при появлении потребителя (A1).
- **Приёмка:** операционная проверка запуска (`public-launch-operations.md`) расширена на воркеры; сбой воркера виден в логах и не влияет на API.

## 6. Нефункциональные требования (для всех эпиков)

- **Безопасность:** код ученика не выполняется в Web/API/Worker вне согласованной ADR границы; все новые таблицы — с RLS; эталоны проверок — защищённый контент; лимиты на всё, что загружает пользователь.
- **Доступность:** WCAG 2.2 AA; новые страницы добавляются в `accessibility.spec.ts`.
- **Производительность:** бюджеты в `tests/e2e/budgets.ts` не повышаются без причины в PR; тяжёлый код загружается по требованию.
- **Наблюдаемость:** новые ошибки инфраструктуры — операционные события по ADR-0052, без персональных данных.
- **Качество:** `pnpm check` локально перед каждым пушем; новый код — с тестами; документация и ADR обновляются в том же PR.
