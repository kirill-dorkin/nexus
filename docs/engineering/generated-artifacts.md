# Generated artifacts policy

Generated files are not source code and must not create persistent working-tree drift.

## Source-controlled artifacts

The following generated-or-derived artifacts are intentionally committed when they are part of the reproducibility contract:

- `pnpm-lock.yaml` — exact dependency graph, generated by the repository-pinned pnpm version and required by CI.
- Database migrations and other reviewed code-generation outputs that are deployment inputs.

## Ignored local/build artifacts

The following are generated by tools and are not committed:

- `next-env.d.ts` — generated by Next.js. Next.js recommends ignoring this file because `next dev`, `next build`, and `next typegen` may regenerate it.
- `*.tsbuildinfo` — TypeScript incremental compilation state; machine/build specific and disposable.
- `.next/`, `dist/`, `.turbo/`, `coverage/` — build, cache, and test outputs.

`apps/web` runs `next typegen && tsc --noEmit` for standalone type checking. This guarantees that Next.js-generated declarations exist on a clean checkout without relying on a committed `next-env.d.ts`.

## Rules

1. Do not hand-edit generated artifacts.
2. A generated file may be committed only when reproducibility or deployment requires it.
3. If a tool modifies tracked files during a normal build/test/dev command, treat that as a repository-policy defect and fix the ownership/ignore boundary rather than accepting working-tree drift.
4. CI must use the committed lockfile with `--frozen-lockfile` once the initial lockfile is committed.
